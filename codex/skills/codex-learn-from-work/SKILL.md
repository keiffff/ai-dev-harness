# Learn From Work

Maintain knowledge that changes later work. Reporting a failed experiment is an observation; when the user requested a working improvement, investigate what prevented it and continue the authorized work.

Use `references/library` to find the record, skill, code or check that owns the observed behavior. Start from the actual request, actions and result, including the user correction. Preserve the original intended outcome and uncompleted work alongside the local failure. Do not turn the latest symptom into a smaller replacement task.

Separate what was observed from explanations not yet tested. Trace discovery, reading, application, execution and result to locate where the knowledge stopped helping. If a record was read but not used, do not assume that adding more records or stricter wording will solve it. Preserve the incompatibility or reason given, or mark it unknown.

Improve the owner that can change the behavior: existing code or executable verification for deterministic faults; an existing skill for reusable work procedure; a local record for concrete context, decisions and source evidence. Prefer an existing owner to another summary, wrapper or parallel workflow. Keep private context in the local library. Only generic instructions and implementations belong in a shared harness.

Retain the failed attempt and its evidence. Tie a candidate change to that failure and the expected observable effect, then run the same relevant work and checks. Keep product acceptance criteria independent of the candidate instructions. Correct test plumbing when it cannot observe the failure; do not weaken the behavior expected of the product or select only favorable attempts.

Update the existing local record file with the correction, source, verification conditions and measured result, including limits or a failed candidate. Here the owning asset means its maintaining file or directory. Perform the authorized local file edit; contacting a person is a separate action and is not how this update is made. A scratch evidence note alone leaves the existing record unchanged. If the record already states the same verified facts accurately, retain the execution evidence without adding duplicate history. Link runnable assets from the topic index so a later agent can discover and execute them. Mark older advice as superseded where the evidence warrants it, preserving why it changed. Do not rewrite unrelated history or promote an agent suggestion to a user decision.

When the local library has an existing `records.json` search view of the same Markdown entry, refresh its duplicated facts after editing the entry with `python3 scripts/sync_record_index.py --index <library>/records.json --entry <maintained-file> --id <record-id>`, using paths resolved from this skill and the actual library. The script changes only that existing record’s body and verification state; it preserves other records, provenance and metadata. The Markdown entry remains the maintained source. This prevents the search view from continuing to return a corrected stale claim.

Verify transfer in a fresh task that has the ordinary skill catalog but has not been handed the relevant record or answer. Check whether it finds, applies and executes the asset, avoids the known failure, completes the requested work and returns any new finding to its owner. Use another relevant task to test reuse beyond the calibration example. Distinguish asset installation, observed behavioral improvement and remaining uncertainty.

If the change does not help, use the new evidence to refine the cause and next change. Do not repeat the same independent experiment merely to obtain a favorable result. A concrete unresolved boundary or required user decision must be stated as such; a completed substep or a negative result alone is not completion of the requested improvement.
