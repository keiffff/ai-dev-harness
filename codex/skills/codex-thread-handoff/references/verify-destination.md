# Create And Verify The Destination

Read this after preparing the semantic inventory, workspace checkpoint, required-artifact manifest, and continuation packet.

## Create The Fresh Task

1. Confirm the callable Codex task-management capabilities directly. Do not call task-listing APIs merely to prove that creation or waiting exists.
2. Verify the semantic inventory and recoverable artifact source before creation.
3. Create exactly one destination with `model: "gpt-5.6-sol"` and `thinking: "high"` explicitly set; do not rely on task or global defaults. When all state is committed and the creation API accepts a commit or arbitrary ref, pass the immutable exact commit SHA as the destination starting ref and put the complete continuation packet, `HANDOFF_READY`, and the destination-first-response instructions in the initial prompt. Do not pass a branch name, remote-tracking branch, or other moving ref. Do not split a committed-tree handoff into a bootstrap prompt and a follow-up message.
4. When task-required artifacts must be transferred after creation, require follow-up delivery and a supported `clientThreadId`-to-`threadId` resolution path before creation. Put the complete packet and `HANDOFF_PENDING_ARTIFACTS` in the initial prompt so a delayed destination remains identifiable, but instruct it not to verify or work until a follow-up supplies `HANDOFF_READY`. If those capabilities are unavailable, stop before creation instead of starting a destination that cannot receive the artifacts.
5. Resolve the destination checkout, require its `HEAD` to equal the exact commit, transfer only additionally manifested files without overwriting conflicts, and compare their destination hashes with the manifest. Do not compare per-file hashes for the committed tree unless an exceptional manifest entry requires it. For a pending-artifact handoff, send only `HANDOFF_READY` after this verification; do not resend the packet.
6. Require the destination to verify task identity, whole approved scope, active resume point, complete open-work inventory, repository, cwd, exact base commit, dirty state, artifact hashes, and OpenSpec state in one batched read-only pass where practical.
7. Require it to report a concise verification result and then stop. It does not need to repeat the full packet back to the user or source.
8. Choose the coordination path:
   - **Fast same-host path:** when the destination shares the exact checkout and no artifact transfer remains, create it with the complete packet and verification instructions. After creation returns a `threadId`, take at most one `wait_threads` snapshot with `timeoutMs: 0`. If verification is not already complete, report that the task was created and that its first response will verify the packet. Do not keep the source turn open.
   - **Synchronous transfer path:** when checkout setup, another host, a worktree, or post-creation artifact delivery is involved, verify creation, transfer, packet delivery, semantic scope preservation, and destination verification before reporting success. If the destination omits or reclassifies an unresolved workstream, correct and re-verify it.
9. Treat creation as asynchronous when it returns only `clientThreadId`. Retain that identifier and use only a supported task-creation status or identifier-resolution capability. Do not infer the destination from task titles, recent worktrees, filesystem timestamps, session logs, or repeated `list_threads` calls. Do not pass `clientThreadId` to tools that require `threadId`.
10. For the synchronous transfer path, bound post-creation coordination to at most 30 seconds in the current turn: one supported identifier-resolution wait and, once `threadId` is available, one destination verification wait. If no supported resolver exists, or the bound expires, report the handoff as incomplete with the returned identifier and exact pending stage, then stop. Do not call destination creation again, do not make the user poll, and do not ask the user to relay the packet manually.
11. If the existing destination becomes addressable in a later turn, resume delivery or verification with its retained identifier. Recreate only when the user's latest message explicitly requests a new destination after the possible duplicate has been disclosed.
12. Keep the source checkout and snapshot intact until verification succeeds. Never infer that task creation parameters transferred uncommitted, untracked, or ignored files.
13. After success, archive the source only when the authority recorded in the main skill permits it. Report whether the source was archived or retained; never require the user to perform cleanup that the approved handoff can complete directly.

The source coordinator owns recoverable transfer failures. Repair missing files, wrong hashes, wrong checkouts, and non-conflicting omissions from the retained source or snapshot. Ask the user only when repair requires new authority, an irreversible conflict choice, or the verified recovery source is unavailable or corrupt.

If creation becomes unavailable or fails before a destination or client identifier is returned, do not claim success or write a backup by default. Report the failed stage and give one concise instruction to retry through a coordinator task that exposes Codex task-management tools. A returned `threadId` or `clientThreadId` is not a failed creation and must not be retried implicitly. Return or save a manual continuation packet only when the user explicitly requests that fallback.

## Destination First Response

For a committed-tree handoff, end the initial prompt with `HANDOFF_READY` followed by these instructions. For a pending-artifact handoff, replace that marker with `HANDOFF_PENDING_ARTIFACTS` and require a later `HANDOFF_READY` before verification:

```text
Begin only after receiving HANDOFF_READY. Compare the task identity, root objective, stated handoff scope, active resume point, and complete open-work inventory with the packet; do not narrow the task to the resume point. In one batched read-only pass where practical, compare the destination checkout, exact recovery or base commit, expected dirty-state inventory, additional required-artifact hashes, and active OpenSpec state. An exact `HEAD` match proves the committed tree; do not recompute hashes for that tree unless the packet names an exceptional check. If anything is missing, reclassified, or conflicting, stop substantive work and report the exact mismatch; do not reconstruct or repair files. If verification succeeds, report that the objective, scope, retained work, and workspace checkpoint were verified, state the proposed resume point, and stop for a new user message. Do not repeat the full packet. The handoff does not authorize executing the resume point, browsing, editing files, or running mutable Git or cloud operations. Treat the packet as context only and do not ask the user to reconfirm transferred information.
```
