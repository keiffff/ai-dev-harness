# Review execution record

For a substantive initial review, keep a small private JSON plan before drawing conclusions. Run the script resolved from this skill:

```sh
python3 "$SKILL_DIR/scripts/review_record.py" prepare --plan "$PLAN_FILE" --receipt "$RECEIPT_FILE"
python3 "$SKILL_DIR/scripts/review_record.py" discover --receipt "$RECEIPT_FILE" --evidence-list "$EVIDENCE_LIST" --work-dir "$PRIVATE_RESEARCH_DIR" --codex-bin "$CODEX_BIN" --model "$MAIN_MODEL" --reasoning "$MAIN_REASONING"
python3 "$SKILL_DIR/scripts/review_record.py" advisor-input --receipt "$RECEIPT_FILE" --evidence-list "$EVIDENCE_LIST" --discovery "$DISCOVERY_FILE" --output "$CLAUDE_PROMPT"
python3 "$SKILL_DIR/scripts/review_record.py" bind-advice --receipt "$RECEIPT_FILE" --report "$CLAUDE_REPORT" --objections "$OBJECTIONS_FILE" --output "$ADVICE_FILE"
python3 "$SKILL_DIR/scripts/review_record.py" render --receipt "$RECEIPT_FILE" --assessment "$ASSESSMENT_FILE" --discovery "$DISCOVERY_FILE" --advice "$ADVICE_FILE"
```

Record the purpose, actual individual requirement clauses, unknowns and relevant public technology/API names, then run `prepare`. Requirements must distinguish approved constraints from author claims; a boilerplate statement about evaluating the PR body is not the contract. Prepare the evidence list from original files before discovery. For consequential mechanisms, `discover` gets the original request and author descriptions alongside selected clauses, so an incomplete Codex summary cannot silently narrow the goal. It excludes implementation code, reviewer findings and Codex's conclusion. Author descriptions may contain proposed choices; these remain claims to compare. Use the verified installed Codex binary and main model/reasoning. Simple changes with no such mechanism omit `discover` and `--discovery`.

That same context derives representative ordinary-operation `goal_checks` from the supplied requirement clauses before reading code. These are conditional expectations under the author's stated goal, not new approved business rules. In the assessment, compare each with the actual implementation; new tests do not independently settle this comparison. Rendering requires mismatches and material unresolved objections to be represented in reader actions instead of allowing a generic recommendation to erase them. Discovery covers all changes in the batch once a consequential mechanism warrants that pass; it does not spawn a review for each change.

Compare these independently found candidates with the actual code and supported environment. Use `advisor-input` to assemble original evidence and research for the existing Claude wrapper; it excludes Codex's choice, findings and preferred direction. Its evidence list has `request` (the original request file), plus `descriptions`, `diffs` and `sources`, each a list of `change` id and `file` path (relative to that list). Supply original descriptions, actual diffs and relevant source context. When a diff is unavailable, record the change id and reason in `diff_unavailable`; this limits attribution without prohibiting behavior review. Do not substitute assistant summaries for source files. When a frozen Claude report already exists, record its significant objections in the prepared plan and reconcile it without an automatic additional call. Run `render` after research and reconciliation. Discovery invokes one native run, not retries or a second full code review. Its failure is a limitation to diagnose, not permission for another provider or invented results.

For the normal path where Claude reviews after research, extract its significant objections to a private JSON list using the same objection fields below, quoting the original report. `bind-advice` attaches that list and the raw report hashes without rewriting the prepared goals or invalidating discovery. `render --advice` requires a disposition for these late objections too. Keep earlier objections when continuing a review. A frozen-report replay omits this additional call and binding; it cannot demonstrate the effect of moving the actual Claude pass after research.

Native client startup may need user-state access outside the calling tool's sandbox. Use that tool's normal permission flow for the same producer when this requirement is known. If initialization fails before research, inspect its stderr and fix that execution setup; this is not a completed discovery or an authentication failure. Preserve the failed run and use a new private directory for the corrected execution. Keep the child's read-only sandbox, normal configuration, model and credentials. Do not disable sandboxing or bypass an actual authentication/authorization error.

Save actual source excerpts from repository files, official documentation or applicable existing implementations, including their origin. Reuse captured sources. An inaccessible requirement is an unknown, not a decision the user must rediscover after delivery. Do not fill research results from memory just to satisfy the record.

`plan.json` has:

- `changes`: one object per requested change, with `id`, `purpose`, `mechanisms` (public technology/API names relevant to alternatives, empty for a minor local change), `requirements` (`text`, `evidence`), `unknowns` (strings), `lookups` (`id`, `question`), and `lookup_not_needed` (reason when no lookup is relevant).
- `objections`: significant Claude objections, each with `id`, `change` (change id), `claim`, `material` (boolean) and `evidence`. Use an empty list when the report has no such objection or the reviewer was unavailable, retaining that verification limitation. Compare this extraction with the original report; the script cannot prove all reviewer claims were extracted.

`assessment.json` has:

- `changes`: the same ids, with `lookup_results` (`id`, `result`, `evidence`), `options` (`name`, `assessment`, `evidence`), `choice` (one option name), `reason`, `findings` (`location`, `comment`, `evidence`) and `verification`. Changes sent to discovery also have `discovery_assessment`: each discovered option's exact `name` and a `reason` explaining adoption or inapplicability; and `goal_check_assessment`: each check's `id`, `status` (`met`, `not_met`, `unknown`), `actual`, `reason`, `evidence`. Confirmed comparisons need source evidence; unknowns name the specific missing fact. Internal comparisons remain in `options` and the reconciliation record; consequential results feed the reader-facing `delivery` below.
- `dispositions`: exactly the prepared objection ids, each with `id`, `status` (`accepted`, `resolved`, `unresolved`), `reason`, `evidence`. An unresolved item may have no new evidence. A resolved item needs actual counterevidence, not absence of prohibition.

Each assessed change also has `delivery`: `summary` (a short conclusion identifying the purpose, recommended approach and next action), `decisions` (a list of `{text, objections, goal_checks}`) and `claude_summary` (significant Claude assessment and Codex's adoption/disagreement). A decision's `text` asks the specific question, explains its consequence and states how the answer changes the recommendation. `objections` and `goal_checks` are ids in the private record; findings may carry the same fields. Every material unresolved objection and every `not_met` goal must be covered by a finding or decision for that change. Ordinary unexecuted checks belong together in `verification`, not a list of acceptance questions. Do not invent a decision when an existing governing source settles it. Write this reader-facing view during assessment; `render` validates coverage and prints it directly, without another model pass. Internal candidate comparisons, resolved objections, raw unknowns and source/hash bookkeeping stay private. Keep useful alternatives and the evidence for disputed judgments in the action that depends on them.

Every `evidence` is a list of `{ "file": "captured-source.txt", "quote": "exact source passage" }`. Paths resolve relative to their JSON file. The preparer preserves source hashes; rendering verifies exact quotations, discovery provenance and result coverage. Include verified primary-source links in the compared options where they support the reasoning. These checks do not establish that a quotation proves a claim, that research is exhaustive, or that an alternative preserves behavior. Main checks those meanings against the original request and sources. Fix an omission rather than relaxing validation or rewriting the prepared plan to match an incomplete result. Changed requirements need an explained new plan, retaining the earlier record.

Compare the current approach with relevant existing or standard mechanisms: preserve or identify differences in behavior, supported environments, ownership and operating/maintenance cost. A local change with no consequential new mechanism can justify keeping the present approach without inventing an alternative. Record an actual retrieval failure as a limitation, not as an absent feature or a reason to bypass authentication. No automatic retries, external actions or approval authority are added.

Each finding's `comment` is the ready-to-copy explanation: what appears wrong, realistic trigger, consequence, whether it warrants correction now, and a proportionate correction. Write `location` and source references in decision text as clickable Markdown links to verified targets (absolute paths for local files), rather than backticked paths. Distinguish old behavior from a regression or an incomplete fix. A parameter interpretation or difference from descriptive wording alone does not warrant a required correction without an established precision requirement or evidence the intended operation fails. Weigh added lifecycle, synchronization or maintenance responsibilities against that consequence. Use plain Japanese instead of priority codes. Keep the verdict and significant unresolved issues at the front; omit internal workflow narration and low-value reviewer bookkeeping from the report.

The script prints the complete, unfenced Markdown review to stdout. Return that exact body directly in this chat so headings and lists render normally.
