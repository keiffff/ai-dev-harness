# Codex Writing

Main owns investigation and judgment; Claude owns substantial reader-facing composition through the configured tool-free wrapper. Ordinary replies and wording-only edits stay in main. Decision records use `codex-decision-doc`, HTML uses `claude-html-report`, and review comments use `codex-code-review`.

## Build The Current Deliverable

1. Select the requested operation before selecting a medium. Turning investigation results or earlier discussion into a report, issue/PR body or named sections is composition, including a short report. A local edit requires an existing supplied draft and a bounded requested change; a brief request to summarize is not itself a local edit. A short acknowledgment, factual answer or shared observation without a writing request stays conversational. Review-comment composition uses `codex-code-review`'s Copyable Review Output on the established findings; it does not require a new code review.
2. Resolve the requested questions before writing. For each missing fact, ask whether it could change the requested conclusion or reader's action. If so, perform the available authorized read in the owning investigation; do not turn unfinished work into an uncertainty paragraph. Do not require universal proof, unrelated measurements or new acceptance conditions. Hand off the original request, original evidence and a short judgment containing purpose, conclusion, required result groups and any pending decision-relevant checks. Use the [composition handoff](references/source-workflow.md) for new or substantially restructured Slack reports, issue/PR bodies and other source-grounded documents. Claude writes the content and layout once; the helper then checks only for sender notes mixed into that actual text and can only delete selected lines. Main does not prewrite a replacement draft. No separate intake, selection, formatting or full-document rewrite loop.
3. A wording-only local edit can stay in main: copy the supplied draft and patch only the requested delta. A factual correction to an ongoing source-grounded report or issue/PR body is still artifact work, even when only one sentence changes: pass the saved draft through the literal-edit path and its final note filter. Do not skip that path as a short conversational reply. Preserve unrequested text. A medium's outline does not authorize adding subjects or commitments from quoted history. An omitted detail needs correction only when it prevents the recipient from performing the requested action or understanding its result.
4. Keep the complete deliverable in one file at the requested destination or private task storage. Explain unfamiliar objects before their names. Preserve source definitions and completion state. A request for a fix plan or recommendation permits proposing an approach from the evidence; label it as a proposal rather than an already adopted or implemented decision. Lack of prior approval is not a reason to replace the requested proposal with an inventory of undecided details. State well-supported findings and explanations directly. Keep the sendable body separate from notes to the user: secondary uncertainty and verification cautions go after the complete body, never into issue/PR/Slack copy. The workflow saves those notes separately as `delivery-notes.md`; do not paste that file into the body. If the evidence strongly favors an explanation and the remaining uncertainty would not change the recipient's takeaway, decision or action, omit the caveat. Use brief wording within the claim when uncertainty matters. Unpublished drafts contain the accepted result, not correction history. Add no unsupported cause, owner, date, commitment or verification claim.

## Slack: Choose The Reporting Job

Use the user's target draft or explicit requested voice; otherwise use plain form. Polite narration in quoted investigation sources does not set the report's voice. For reports with multiple points, put short section names in inline backticks and organize each section as hierarchical bullets. The parent states the point; children carry its reasons, evidence and conditions. Follow the supplied section names. A short acknowledgment or a single brief answer stays plain. Compose this layout directly; do not make a separate formatting call. Use no outer fence, Markdown hash headings or tables unless requested.

| Job | Build the message from |
|---|---|
| Investigation results | Overall conclusion, then the findings across the requested questions. Retain distinct result groups and the difference between observed events and estimates. End with an action only when it was requested or agreed. |
| Incident report | Event and impact, then cause and detection gap, then completed and remaining measures. Derive each measure from existing behavior, the uncovered path and the actual change; do not propose an existing mechanism as new. |
| Interim findings | What was observed and what it supports. Include unresolved causes or boundaries only where they change the conclusion or next action. |
| Progress update | What is complete and its visible result, then close with what remains and its actual dependency. Include a next action only if requested or agreed; no internal inventory. |
| Verification request | Intended send time and environment, the changed behavior, supplied reproduction actions and expected visible result. Include only what the recipient needs to verify; other recovery work is a separate subject. |

For a short acknowledgment or local wording edit, preserve its size and intent rather than building a report.

## PR Body

Use the final change set and accepted purpose as the source. Group changes by resulting behavior, not by edit chronology. Fill the repository template with the problem, resulting behavior, relevant rationale and verification actually performed. Use complete, natural Japanese sentences in です・ます form unless the user or repository supplies another convention; headings, identifiers and compact table cells may remain labels. Slack's plain-form convention does not carry into PRs. Explain which component reads, selects, stores or changes which object, and the resulting behavior; replace vague translated abstractions with those concrete relationships without removing identifiers or technical detail. Describe implementation safeguards directly; reserve measurement claims for measured comparisons. Make the body understandable without this conversation.

When background or detail is requested, retain why the final approach was chosen and relevant constraints or alternatives. New issue/PR bodies use the composition handoff; existing bounded edits preserve the supplied draft. Use the current completed work state rather than carrying an earlier issue's provisional assessment into a completed PR. Select exact spans of internal notes and delete them from the saved draft. Keep the remaining wording intact. If a deletion leaves a broken sentence, repair that sentence locally and check it against the original evidence:

- **Change and rationale.** Keep the trigger, resulting behavior, adopted rationale and compatibility or rollout constraints. Leave abandoned attempts, investigation chronology, agent handoffs, worktree setup and drafting steps in the work notes.
- **Verification.** Keep the relevant condition or operation and what happened. Retain, for example, whether a failed save left data unchanged, or the workload and conditions needed to compare timings. Include suite names, counts, commands or fixtures when they establish relevant coverage or help reproduce that result. Leave test file inventories, worker settings and rerun history in the work notes when they add no such evidence. Keep mock conditions, environments and sample sizes attached to the specific check they describe.
- **Failures and unknowns.** For each proposed qualification, identify the exact claim it changes or the accepted behavior or release condition that remains unmet. Keep it when that link has a concrete consequence for the reviewer, and state that consequence. Otherwise delete the qualification from the saved body. Keep the supported explanation around it. Claims introduced while drafting do not create new acceptance conditions. Execution restrictions, handoff records, publication progress and unrelated unperformed checks belong in the task's delivery record.

README follows the same reader-first ordering; release notes give user-visible changes; UI copy explains the event and the next available action.

## Receive And Deliver

If composition returns a concrete evidence question, resolve it in the owning investigation and update the same handoff before composing again. Do not append the question to the sendable body. A completed body needs a direct source check in main: requested results, quantities, mechanisms and completion state survive, and no unsupported claim was added. Correct factual defects through the writer with specific evidence; do not rewrite its style. Show the complete saved body under AGENTS.md's format, without regenerating it during delivery. Put useful sender notes outside the copy. An unchanged complete artifact needs no repeated call.

Prefer the user's accepted example. When a new structure needs a model, read only the matching section of [Japanese prose examples](references/japanese-technical-prose.md); follow its information order, not its incidental facts. PR and review Markdown follow AGENTS.md's complete copyable-body contract.

This editing check is not independent proof. When changing the skill, compare actual old/new artifacts on the same requests and corrections; do not make that evaluation a step in every writing task.
