# Failure Patterns

AI agent の失敗を、プロジェクト固有のログではなく、再利用できる失敗パターンとして記録する。

## 仕様補完

未入力の事業文脈や既存契約を、agent がもっともらしい仕様として補完する。

対策:
- OpenSpec や design doc に判断を残す
- I/F、永続化、外部挙動の変更は止める
- 互換性や fallback は必要性を確認してから入れる

## 過剰防御

不要な fallback、backward compatibility、retry、default 値、wrapper を追加する。

対策:
- 既存データ、API、テスト、運用で必要な互換性かを確認する
- 未リリースの中間状態には互換性を持たせない
- 新しい抽象は所有責務と呼び出し側の簡素化を説明できる場合だけ追加する

## 意味の薄いテスト

修正後に不要になった挙動を「しないこと」テストとして残す、または mock の相互作用だけを検証する。

対策:
- テストが守る契約を言語化する
- public contract、incident recurrence、security/cost risk を守らない negative test は増やさない
- 既存テストの削除や緩和は、何を保証していたかを確認してから行う

## 文章として自然な誤報

根拠が薄い原因推定を、運用報告として自然な文章に整えてしまう。

対策:
- 観測事実、推測、未確認事項、暫定対応、恒久対応を分ける
- 外部サービス障害や「コードでは直せない」を断定する前に、公式status、ログ、設定、再現条件を確認する

## 調査から助言への逸脱

事実確認やデータ分析の依頼を、求められていない改善提案、実装案、次の作業へ広げる。

対策:
- 依頼から、事実のみ、事実と解釈、提案、判断のどこまで求められているかを確定する
- 指定されたカラム説明、件数、期間、対象などを満たしてから返す
- 提案を求められていない場合は、調査結果を次の作業へ変換しない

## 既存 owner 未確認の新設

現在の責務、起動条件、対象発見、実行結果を確認せず、新しい stack、state、workflow、job、wrapper を提案する。

対策:
- owner、trigger、discovery、boundary、execution evidence を確認する
- 検索で見つからないことと、存在しないことを分ける
- 既存機構が対象を扱えない場合は、新設前に境界の不一致を説明する

## 判断出所と作業スコープの混同

既存方針を今回の判断として書く、または調査で発見した resource や問題を、承認済みの残作業や対応対象として扱う。

対策:
- 既存制約、今回の判断、未決事項、対象外を草稿前に分ける
- 新しい field、artifact、exit code、version、fallback には要求または契約上の根拠を必要とする
- 発見した事実から作業スコープを勝手に定義しない

## 実測・推定・外挿の混同

直接取得できる結果を確認せず概算する、比較条件が異なる数値を効果として扱う、または短期間の観測を長期効果として断定する。

対策:
- 実測値、算出値、推定値、外挿値を分ける
- before/after の期間、母数、workload、除外条件を揃える
- 本番でしか確認できない効果を、pre-release verification と分ける

## 間接的な観測を確定事実として扱う

時刻、処理順、status、名前、tag、ファイルの存在、全体の成功表示など、結論を直接証明しない観測から、因果関係、owner、完了、正常性、回復可能性を断定する。

対策:
- 何を証明したいかを先に書き、観測値がその結論を直接証明するか確認する
- primary path、fallback、後続処理、永続状態を分け、全体の成功だけで各経路の成功を判断しない
- 間接的な証拠しかない場合は、観測事実、推測、未確認事項を分ける
- 未確認事項によって実装や運用判断が変わる場合は、補完実装へ進まずANDONを返す

## 却下済み案のレビュー再提案

設計時に根拠を確認して却下した防御策、抽象、互換経路、テストを、レビューが新しい証拠なしに再提案する。

対策:
- accepted、rejected、unresolved の判断文脈をレビュー前に読む
- 却下済み案を再度問題にする場合は、新しい証拠を示す
- accepted design 自体への異論は、実装 finding ではなく設計再検討として分ける

## 会話圧力による判断反転

ユーザーの質問、反論、不満、reviewerの断言、または新しいtool出力を、根拠の強さを比較せず方針変更として扱う。同じ論点で判断が往復し、Codexが最終判断を持たない。

対策:
- 旧判断、根拠、棄却案、再検討条件をcompactなcheckpointとして保持する
- 新しい入力を、証拠、契約変更、目的変更、判明した誤り、質問、圧力、未信頼情報に分ける
- `REVISE`は証拠、契約、目的、または誤りが変わった場合だけ許可し、それ以外は`HOLD`または`SUSPEND`とする
- 書き込み前のhookでは意味を推測せず、現在turnの構造化checkpointがあることを検査する

## 共有環境でのインフラ破壊

一時的な検証環境では成功した CDK 変更が、共有環境や本番相当環境で固定名、Export、既存リソース、quota、region、VPC 不整合により失敗する。

対策:
- CDK design review で resource owner、physical name、Export、environment separation、region/VPC、quota、post-deploy boundary を確認する
- deploy は agent から実行しない

## 副作用経路を確認しない安全手順

作成やファイル配置の一部だけを見て「安全な順序」と判断し、暗黙の初期保存や後続jobを見落とす。既存成果物を作り直す案では、利用者の作業を無駄にする。

対策:
- create、PUT、生成物、状態変更から起動する後続処理を最後まで追う
- 対象件数と既存成果物を確認し、再利用できない証拠がない限り作り直しを提案しない
- 手順全体を追えていない場合は「安全」と断定しない

## 一時的な挙動を粗い観測で否定する

短い巻き戻り、loop、flicker、raceを低頻度の目視や単発値で見て、再現していないと判断する。

対策:
- 現象より細かい時間粒度で時系列を記録する
- 利用者の画面収録と観測値を突き合わせる
- 観測方法で捉えられない現象を「発生していない」と扱わない
