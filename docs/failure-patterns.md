# Failure Patterns

AIエージェントの失敗をプロジェクト固有のログで終わらせず、再利用可能な失敗パターンとして記録する。

## 仕様補完

未入力の事業文脈や既存契約を、エージェントが推測によってもっともらしい仕様として補完してしまう。

対策:
- 判断の根拠を OpenSpec や design doc に記録して残す
- I/F、永続化、外部挙動の変更を伴う作業はいったん止める
- 互換性維持や fallback の追加は、事前の必要性を確認してから実施する

## 過剰防御

不要なフォールバック、後方互換性、再試行、デフォルト値、ラッパーを追加してしまう。

対策:
- 既存データ、API、テスト、運用の各観点から、本当に必要な互換性であるかを確認する
- リリース前の開発中間状態に対しては、互換性を持たせない
- 新たに抽象化を導入する場合は、所有責務が明確であり、呼び出し側を簡素化できる理由を説明できる場合に限定する

## 意味の薄いテスト

仕様変更によって不要になった古い挙動を「特定の動作をしないこと」のテストとして残し続けたり、mock 間の相互作用だけを検証したりする。

対策:
- 各テストが守るべき契約を明確に言語化する
- public contract、incident recurrence、security/cost risk のいずれも保護しない negative test は増やさない
- 既存テストの削除やアサーションの緩和を行う際は、そのテストが本来何を保証していたかを事前に確認する

## 文章として自然な誤報

根拠が不十分な原因推定であるにもかかわらず、運用報告として体裁の整った自然な文章にまとめてしまう。

対策:
- 報告内容において、観測事実、推測、未確認事項、暫定対応、恒久対応を明確に区別する
- 外部サービス障害や「コード側では修正不能」と断定する前に、公式status、ログ、設定内容、再現条件を確認する

## 調査から助言への逸脱

事実確認やデータ分析の依頼であるにもかかわらず、指示されていない改善提案、実装案、次の作業計画にまで範囲を広げてしまう。

対策:
- 依頼内容から、事実の提示のみか、事実と解釈までか、提案や判断まで含まれるのかを確定する
- カラム説明、抽出件数、対象期間、分析対象など、指定された要件をすべて満たした上で回答する
- 提案を求められていない場合は、調査結果を勝手に次の作業計画へと変換しない

## 既存 owner 未確認の新設

既存コンポーネントの責務、起動条件、対象リソースの検出方法、実行結果を確認しないまま、新しいスタック、状態、ワークフロー、ジョブ、ラッパーを提案してしまう。

対策:
- 既存の owner、trigger、discovery、boundary、execution evidence を事前に確認する
- 検索で見つからないことと、実際には存在しないことを明確に区別して調査する
- 既存の仕組みが対象を扱えない場合は、新設に着手する前に責務境界の不一致を説明する

## 判断出所と作業スコープの混同

既定の方針をあたかも今回の判断であるかのように記述したり、調査過程で発見したリソースや課題を、承認済みの残作業や対応対象として勝手に組み入れたりする。

対策:
- 草稿を作成する前に、既存制約、今回の判断、未決事項、対象外スコープを明確に整理・分類する
- 新しい field、artifact、exit code、version、fallback を追加する際は、要件定義または契約上の明確な根拠を必須とする
- 調査で発見した事実のみを根拠として、作業スコープを独断で再定義しない

## 実測・推定・外挿の混同

直接取得できる検証結果を確認せずに概算で済ませたり、比較条件が揃っていない数値を改善効果として扱ったり、短期間の観測結果を恒久的な長期効果と断定したりする。

対策:
- 実測値、算出値、推定値、外挿値を明確に区別して記録する
- before/afterの比較では、対象期間、母数、workload、除外条件を揃える
- 本番環境でしか確認できない効果と、pre-release verification で検証可能な効果を明確に分離する

## 間接的な観測を確定事実として扱う

タイムスタンプ、処理順序、status、リソース名、tag、ファイルの存在、ジョブ全体の成功表示といった間接的な観測結果から、因果関係、owner、完了状況、正常性、回復可能性を性急に断定してしまう。

対策:
- 証明したい命題をあらかじめ明確にし、得られた観測値がその結論を直接証明しているかを確認する
- primary path、fallback、後続処理、永続状態を個別に区別し、プロセス全体の成功表示だけで各経路の成功を判断しない
- 間接的な証拠しか得られない場合は、観測事実、推測、未確認事項を明確に切り分ける
- 未確認事項の内容によって実装方針や運用判断が変わる場合は、推測に基づく補完実装を進めず、ANDONを返す

## 却下済み案のレビュー再提案

設計段階で根拠を検証した上で却下された防御策、抽象化、互換経路、テストケースを、コードレビュー時に新たな証拠がないまま再び提案してしまう。

対策:
- レビューに着手する前に、accepted、rejected、unresolvedの各判断文脈を読む
- 一度却下された案を再度論点として提起する場合は、前提を覆す新しい証拠を提示する
- すでに合意された accepted design そのものに対する異論は、実装上の指摘（finding）と混同せず、設計の再検討事項として明確に切り分ける

## 会話圧力による判断反転

ユーザーからの質問、反論、不満の表明、レビュアーによる断言、あるいは新たなツール出力に直面した際、根拠の妥当性を比較検討することなく方針を変更してしまう。その結果、同一の論点で判断が二転三転し、Codex が一貫した最終判断を保持できなくなる。

対策:
- 過去の判断内容、その根拠、棄却した代替案、再検討すべき条件を、簡潔（compact）な checkpoint として記録・保持する
- 新たに得られた入力を、証拠、契約変更、目的変更、判明した誤り、質問、圧力、未検証の情報のいずれかに分類する
- `REVISE` は証拠、契約、目的、または誤りが変わった場合のみ許可し、それ以外の入力に対しては `HOLD` または `SUSPEND` とする
- 変更書き込み前のhookでは文脈の意味を推測せず、現在のターンに対応する構造化checkpointが存在することを確認する

## 共有環境でのインフラ破壊

一時的な検証環境では正常に動作した CDK の変更が、共有環境や本番相当の環境に適用された際、リソースの固定名競合、Export 名の不整合、既存リソースとの衝突、quota 超過、リージョンや VPC の設定不整合によって失敗する。

対策:
- CDK design reviewにおいて、resource owner、physical name、Export、environment separation、region/VPC、quota、post-deploy boundaryを確認する
- deployはエージェントから実行しない

## 副作用経路を確認しない安全手順

リソース作成やファイル配置といった一部の操作手順だけを見て「安全な順序」と安易に判断し、暗黙的に発生する初期保存や後続ジョブの自動起動を見落としてしまう。また、既存成果物を安易に再作成する手順を提示し、利用者の作業成果を無駄にしてしまう。

対策:
- createやPUT、成果物の生成、状態変更を契機として起動する後続処理を最後まで追う
- 対象件数と既存成果物の有無を事前に確認し、再利用できない明確な証拠がない限り、作り直しの提案は行わない
- 一連の手順に伴う副作用を最後まで確認できていない段階では、その手順を「安全」と断定しない

## 一時的な挙動を粗い観測で否定する

短時間の状態巻き戻り、ループ、画面のちらつき（flicker）、競合状態（race）などの一時的な不具合を、低頻度の目視確認や単発の値確認だけで「再現しない」と判断してしまう。

対策:
- 発生している現象より細かい時間粒度で、時系列データを収集・記録する
- 利用者から提供された画面収録と、システム側の観測ログを時系列で突き合わせて検証する
- 現在の観測方法やサンプリングレートでは捉えられない現象を、「発生していない」とみなさない
