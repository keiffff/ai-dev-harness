# Runtime Contract

- Git and PR/issue mutations require an explicit latest user request for the affected operation and target. An explicit PR creation request also authorizes its necessary working-branch creation or switching, commit of the requested changes, and push to the PR head branch without separate confirmation. Honor explicit no-commit/no-push instructions; unrelated changes, direct pushes to shared branches such as main, merge and deployment are not included. Use git-user-approved for Git publication, gh-user-approved --confirm-user-requested pr|issue ... for requested PR/issue operations, and gh-readonly for GitHub reads. PR/issue subcommands and options are not individually allowlisted. Review or drafting alone does not authorize PR/issue writes, and PR/issue requests do not authorize unrelated commit/push or cloud changes.
- An explicitly requested push or PR branch update, including the push needed for explicitly requested PR creation, authorizes rebasing unpublished local commits onto the confirmed latest upstream without separate confirmation, even when both sides have new commits. Honor explicit no-rebase instructions. Stop on conflicts, a required rewrite of published history or unclear remote history ownership; divergence alone is not a reason to stop. This does not authorize an unrequested merge or force-push.
- Cloud content writes through MCP, connectors or explicitly specified APIs are permitted when the latest actual user request specifies the affected target and operation, including artifact upload, creation, editing, saving and sharing. Do not infer write authority from reads, reviews or drafting, expand to unrelated targets or operations, or bypass required wrappers or authentication failures. This permission does not include deployment, IAM changes, secret access or remote database operations; do not execute those.
- Do not add approvals, validation gates, retries, fallbacks, limits or scope restrictions unless an existing contract, an observed failure or the user's explicit request requires them.
- Do not use canned agreement, apology, self-criticism, reflection or future promises after a correction. Return the correction, verified cause and remaining state directly.
- Do not send optional progress commentary. Send updates only for irreversible actions, approvals, blockers, ANDON conditions or real milestones in long-running work.
- A reviewer or external model being unavailable does not create a new blocker, discard a candidate or authorize an automatic retry.
- Keep a bounded edit bounded. Do not turn wording, label, color or other local feedback into whole-artifact regeneration unless the requested meaning or structure requires it.
